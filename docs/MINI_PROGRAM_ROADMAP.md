## 产品与端的分工

| 端 | 后续职责 |
| --- | --- |
| 微信小程序用户端 | 扫码入场、十题探索、虚拟头像、推荐与邀请、双方独立确认、下一站及同舟自愿填报 |
| Web 现场运营 | 活动状态、现场任务、帮助与相遇点管理 |
| Web 同舟资料端 | 仅查看已授权资料；后续婚介服务仍在线下完成 |
| Web 现场大屏 | 保留现有视觉、二维码与动效，通过受控公开投影更新现场数据 |
| 正式服务端 | 身份、权限、数据持久化、并发规则、跨设备同步与资料撤回/删除 |

## 可复用内容与需要适配的部分

- 优先复用题库、品牌、素材、数据类型、纯业务规则及既有验收场景。现有领域代码中的时间、身份和持久化入口需在正式服务端重新核对，不直接信任客户端 actor 参数。
- 当前手机 UI 依赖 Next.js 导航、DOM、浏览器存储、Web Locks 与 BroadcastChannel；小程序应按目标端组件、导航、生命周期和存储接口适配。
- 动效以现有视觉语义为基线，重新验证小程序中答题切换、前后台恢复和减少动画体验，不承诺现有 DOM/WAAPI 实现可直接复用。现场大屏本身继续使用 Web。
- 候选路线为 React + Taro，框架版本与部署服务尚未确定。Taro 官方文档说明其支持 React 与微信小程序，但组件、API、路由等规范与 Web 存在差异；该能力不等于现有 Next.js 工程可自动转换。[Taro 介绍](https://docs.taro.zone/docs/)、[React 使用差异](https://docs.taro.zone/docs/react-overall)。

## 正式后端边界

当前完整 DemoState 仅用于虚构浏览器演示。正式阶段分别提供本人数据、获授权同舟资料和大屏公开投影，禁止将整份客户资料快照分发至所有用户或大屏。

身份与本人操作、双向独立确认、同舟授权状态、撤回/删除及延迟请求校验应在服务端执行；本地角色切换不能用于正式认证。扫码/邀请/相遇计数仍由真实业务事实产生，不能由展示动画或页面访问增加。

## 分阶段实施

1. **现在：本地 V1.0 验证。** 完成品牌统一，保留现有功能和已存演示资料，先由用户体验。
2. **后续计划确认。** 明确小程序主体与账号、正式服务端、接口分工、真实资料范围、预算和部署环境；制定单独计划并获得确认。
3. **适配与联调。** 开发用户端与受控服务端，保留 Web 运营/同舟/大屏；用测试身份和虚构数据联调。
4. **开发者工具与真机验证。** 检查扫码进入、登录续接、两个真实设备的独立确认、断网与前后台切换、资料授权、性能和大屏更新。Web 测试通过不能替代这一阶段。
5. **发布准备与授权。** 届时按微信官方最新要求核对名称可用性、适用类目、AppID、服务域名、隐私材料及提审要求；用户确认发布后才进入正式提审/发布。

本轮没有安装小程序框架、申请账号、创建云资源、提交审核或发布。微信官方具体平台规则需在实际启动时重新核实；现有产品中文名与 V1.0 命名不代表已获平台名称或类目核准。

## 1. 结论

当前阻止再次参与的是原身份的“已离场”状态，不是二维码失效。2026-10-15 的现场管理方案明确规定：管理员离场之后，刷新、重连、修改资料和继续探索均不得自行恢复，只有管理员恢复入场可以恢复同一身份。因此当前表现与原方案一致；如果日常离场用户需要自行返回，应调整业务规则并提供独立的主动重入流程，不能只改手机提示或取消服务端拦截。

本轮只核对现有源码、历史方案及已有测试，并在内存中演练领域状态转换；没有登录实际管理后台、访问用户数据库或进行线上扫码复现。不能据此断言某个已部署实例与本地提交完全一致。

## 2. 代码证据与原因链路

1. `src/domain/commands.ts:335–351`：管理员 return 将 present=true、paused=false、ready=false；leave 将 present=false、ready=false，处理求助并取消当前未完成邀请。参与者记录和历史保留。
2. `src/server/service.ts:133–180`：H5 join 先读取原 Cookie 对应的服务端会话。只要原 participant 还在名单里就返回原身份，即使 present=false；explicit=true 也不会让这个分支自动恢复在场。新 Cookie 会话有效期为30天，但实际身份复用还取决于会话是否有效。
3. `src/server/wechat-service.ts:99–136`：小程序 miniEnter 对同一微信身份、同一活动、同一 epoch 复用原 actor；找到记录即返回，不将 present=false 恢复为 true。重登并不会必然创建新人。
4. `src/features/mobile/MobileApp.tsx:71–91`、`miniapp/src/pages/index/index.tsx:411–420`：手机端识别 present=false 后显示“已离场，请联系工作人员恢复入场”，缺少自助重入入口。
5. `src/server/service.ts:325–333`、`src/server/field-guard.ts:3–10`、`src/domain/commands.ts:38–40`：服务端与领域层继续拒绝离场用户的现场操作。头像、部分卡牌授权写入也使用 fieldParticipant 检查。
6. `src/components/LiveControls.tsx:66–72` 的“重新进入现场”处理的是“本轮参与已结束”的410分支，不是原参与者仍存在但 present=false 的情况，不能直接解决本问题。
7. `docs/weapp/14-field-management.md:24` 与 `plans/archive/2026-10-15-运营后台活动管理与现场清理.md` 明确规定管理员恢复；`tests/live/field-management.test.ts:256–284` 对此已有回归断言。
8. 小程序 `GET /api/mini/enter` 和 `POST /api/mini/enter` 都会调用 miniEnter。后续不能简单在 miniEnter 遇到离场时自动恢复，否则普通读取也可能撤销管理员的离场操作。

链路：管理员离场 → 原身份 present=false → 再扫码复用原身份 → 手机显示离场、服务端拒绝写入 → 必须管理员恢复。

## 3. 现有版本立即可用的解决办法

在正确活动下，进入“现场参与者”列表，筛选“已离场”，勾选该用户，点击“恢复入场”并确认。支持选择多个用户批量恢复。用户再扫描同一个现场互动码或重新打开页面即可同步恢复结果。

恢复后 ready=false，不会自动被推荐给他人。用户需继续完成资料/答题，并根据页面主动选择“我现在可以见面”或继续探索。若仍无法入场，先核对管理员是否恢复了同一活动中的同一个身份、现场是否开放，及该人是否实际被“从本场移除”；这些状态不能用普通恢复混同处理。

不用清空整场、删除用户或清除浏览器 Cookie。清 Cookie/换浏览器会制造匿名新人并影响身份连续性，不是本问题的修复方案。

## 4. 推荐的产品规则：再次扫码后，用户主动重新入场

建议采用最小业务调整：普通“标记离场”视为出勤状态，允许本人在活动仍开放时通过专用按钮再次入场；继续保留管理员恢复入口，以及关闭现场、暂停推荐、从本场移除等现有管理能力。

### 交互优化：统一入口，管理员零操作

- 日常流程：管理员标记离场 → 用户再次扫码 → 点击一次“进入现场互动 / 继续参与” → 系统校验并恢复原身份。管理员无需查找用户或点击恢复。
- 小程序复用现场欢迎页现有的“进入现场互动”按钮。若点击时识别到同轮次原身份已离场，在同一次用户操作中调用受鉴权的重入服务；成功后进入原参与流程，避免先跳转到离场页，再要求第二次点击恢复。交互页已经打开时，也直接提供“继续参与”。
- H5 在离场状态页提供“继续参与”，说明“本次返回会保留你的资料与答题进度”。按钮点击成功后恢复流程；打开原页面同样可操作，不强制用户必须重新扫码。
- 入口先按会话与当前服务端状态区分首次入场、仍在场、普通离场和不可入场，不要求用户理解这些状态。普通离场的恢复仍通过专用重入写接口完成，不把隐式读取改成恢复操作。
- 管理端“标记离场”的确认说明同步改为：停止当前互动，本人可在现场开放期间主动再次入场。保留人工恢复作为备用功能，日常不依赖它。
- 本版不增加活动级开关、冷却时间或新封禁功能。活动关闭、移除、暂停推荐仍按现有权限处理；普通离场不是禁止返回。

完全不点击、只要二维码页面打开就自动恢复，不作为本版目标。H5 二维码地址访问不能可靠证明刚发生一次扫码；小程序现有入口也没有向服务端提供一次新扫码的独立证据。统一的一次点击可表达本人返回意愿，同时避免旧页面刷新立即撤销离场。

| 场景 | 建议行为 |
| --- | --- |
| 同活动、同轮次，原身份已离场 | 欢迎页复用“进入现场互动”，离场页提供“继续参与”；本人点击一次即恢复同一身份 |
| 原身份仍在场 | 正常继续，不创建重复参与者 |
| 被暂停推荐 | 可恢复出勤，但保留 paused 状态；不能自行解除管理员暂停推荐 |
| 从本场移除 | 维持原限制，不能通过普通重入重新生成身份；提示联系工作人员 |
| 现场已关闭 | 不允许重入，显示现场未开放 |
| 本轮已清零、进入新轮次 | 按既有显式新轮入场规则建立新轮身份，不复活旧轮身份和请求 |
| 活动暂时暂停新邀请 | 保留该限制；恢复出勤不等于恢复新邀请 |

这是对旧“只有管理员能恢复”规则的明确调整，须用户确认本计划后才能实施。若业务还需要独立的“禁止再次入场/强制限制”能力，建议另设明确状态与操作；本计划不把普通离场兼作封禁，也不新增该功能。“从本场移除”继续维持原有清理语义，不作为日常离场替代操作。

不建议在每次打开二维码地址、刷新、轮询或 SSE 重连时自动恢复：这些请求与实际重新扫码不能可靠区分，会让管理员刚操作离场就被旧页面的同步请求撤销。

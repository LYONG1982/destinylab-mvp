## 一、目标和交付范围

在 `/screen` 第一屏“今天，想怎样遇见？”中，将统计进度条及该屏原有无分组头像网络，替换为按真实答案聚集的 2.5D 关系场。保留品牌、标题、鼓楼背景、二维码、外层 16:9 框架、四态轮播及另外三个状态的现有业务表现。

关系场使用原生 Three.js；答案、人数、百分比、提示信息继续使用 DOM。手机答题通过现有本地数据链路触发更新，具备头像时沿柔和曲线进入对应场。视觉保持米白、酒红、哑金、低密度和秋日电影感。

本次不新增跨设备后端，不发布线上或微信小程序，不改变手机答题顺序、十道题内容、头像选择流程、推荐算法、双向确认规则、同舟婚恋资料或数据库结构。不将演示数据称为生产数据。

追加实施范围：大屏代表头像显示用户已提交的昵称；手机见面页面简化为点位编号与“缘分相遇码”。仅改变这些展示与说明，不改变见面分配、出发/到达/完成状态及码的生成和核对规则。

## 三、需要在本次确认中明确的产品适配

### 1. 首次答题早于头像选择

实际旅程是首次答题 → 看结果 → 完善昵称/头像。不能在第一次选答案时展示用户尚未选择的头像。

- 首次答题：对应场的真实人数、比例平滑变化；尚未提交昵称/头像时只产生聚合微波纹。
- 完成头像资料：把所选虚拟头像送入已选择的关系场；**不得再次增加回答人数**。
- 已有资料的参与者新增回答：可以一次完成“所选头像入场 + 人数增加”。
- 已回答者改选：头像移至新场，旧场人数减少、新场增加、总人数不变；提示“有人更新了选择”，不称作新用户加入。
- 初始加载、刷新、返回该屏：展示当前快照，不将已有全部参与者重播为新增事件。

验收覆盖上述完整旅程，并用现有 domain command 驱动“已具备头像、尚未回答的测试参与者选择答案”的单次入场案例，验证 59 → 60，并显示真实测试昵称（如“晚风”）。百分比按真实分母计算，不强求文档示例中的 41% → 42%。

### 2. 显示昵称与头像分组（按用户最新要求修订）

用户已明确要求昵称展示，不再以“探索者 001”或“晚*”替代已提交昵称。大屏展示范围调整为“活动昵称 + 所选虚拟头像 + 当前展示问题的选项归属”。这里使用活动 Participant.name，不读取同舟服务申请中的真实姓名。

- 已完成资料的代表头像旁直接显示其活动昵称，入场提示显示“刚刚，『晚风』加入了『一起逛逛』”。第一屏采用 DOM 中文标签；其他状态复用现有节点显示路径同步昵称，布局拥挤时降低代表节点数量，不能又把昵称改成匿名代号。
- 昵称沿用输入端长度/字符校验，作为文本安全渲染，不注入 HTML。长昵称仅按排版省略，不做脱敏；同名用户由内部 visualKey 区分，不向观众暴露业务 ID。
- 只输出昵称、当前展示问题的 optionKey、内部 visualKey、白名单 avatarUrl 和必要视觉参数。
- 原始 participantId 留在适配器内部；稳定布局种子也在内部由 ID 派生，不把业务 ID 传到 DOM、Canvas 元数据或提示文案。
- 不输出其他题目答案、联系方式、同舟资料、相遇地点或缘分相遇码；不展示两名具体用户之间的双向关系。
- 仅当昵称尚未提交、数据缺失或高峰合并时使用“又有 1 个人选择了『一起逛逛』”等聚合文案。完成资料入场与新增回答使用不同语义，避免重复报数。编辑已提交昵称只更新对应节点文字，不触发新增参与者。
- 手机现有资料说明同步提示：“你的昵称、所选虚拟头像及当前大屏问题的选择会在现场大屏展示。”沿用现有说明区域，不新增强制弹窗或改变填写流程；已有推荐可见范围说明保留。
- 不因存在共同选项而宣称“匹配成功”；当前数据不提供可公开的真实配对连接，故不新增两个可识别头像之间的匹配连线。

### 3. 统计人数与代表头像不是同一个集合

当前 Q1 统计来自 `state.responses`，包含历史匿名记录；头像来自当前在场、具有有效虚拟头像的参与者。现有演示种子是 143 条回答、37 位在场参与者，不能画出 143 个“真实参与者头像”。

- 人数、比例和总数继续取既有权威统计投影。
- 代表头像只从满足展示条件且确有该答案的人中稳定抽样，少于容量时不填充虚构人物。
- 展示人数与代表头像数量不要求相等；保留“代表头像展示”这一产品解释，避免误读。
- 无法对应到个人的历史统计变化只更新聚合数字，不制造个人加入事件。

### 4. 多答案能力与轮换问题的边界

现有业务没有 Q1 → Q2 自动换题机制。本次将布局做成接受 Question/Options 的通用组件，支持 2/3/4 个选项和输入问题变化时的过渡；通过隔离的开发预览/测试夹具验收。

正式 `/screen` 仍展示 Q1，不新增选题后台、自动轮题或另一套计时器。未来接入其他当前问题时可复用组件。本次不改变十题问卷，也不为了双选布局修改现有题目。

### 5. 长时间验证必须实测

现有 Canvas 2D 曾做约 10 分钟压力验证，不能据此证明新 WebGL 场景连续 4 小时稳定。此次保留真实墙钟时间至少 4 小时的持续运行验收，单独记录运行设备、浏览器、质量档位、实际时长和指标。短测、加速计时和旧报告均不能替代。

### 6. 见面信息精简与名称统一（用户追加）

只读检查发现两个实际展示位置：M08 双向确认页的相遇票券显示 `point.location`；M09 见面页显示“见面地点 + location”“步行约 distance 米 + 跟随现场指引”。这些文案来自演示点位配置，不是动态定位。

- M08 移除具体方位行，保留真实分配到的点位名称（如 `Meet01`）、对方是否出发及原按钮。
- M09 移除整块“见面地点”与整块“步行约 … 米”，包括相关图标和“跟随现场指引，轻松找到见面点”；不再用默认 40 米补齐。
- 见面票券保留点位编号（如 `Meet01`），与现场打印标识一致；必要说明仅为“请前往现场标有 Meet01 的相遇点”，其中编号取实际分配值，不写死桌子或方位。
- “本次辨认码”统一改为“缘分相遇码”，说明改为“到场后核对昵称与缘分相遇码，不凭虚拟头像认人。”
- `Meet01` 是物理点位编号，`inv.code` 是本次双方核对的缘分相遇码，二者不能混为一个编号；只改后者的展示名称，保留现有值、生成规则和业务字段名。
- `point.location`、`point.distance` 数据字段及已有数据保留兼容；不做 Schema 迁移，不改后台点位管理或商户去向。未分配相遇点仍维持现有等待状态，不默认显示 Meet01。
- 同步当前产品文档中的用户可见术语；历史验收记录保留当时事实，由变更记录说明本次替代，不篡改历史证据。

## 四、最小技术方案

### 数据与事件

沿用 `Business state → ScreenAdapter → ScreenSnapshot → MotionController → visuals`，不创建第二个业务 store、通信服务或独立统计口径。

1. 为视觉快照增加当前问题、选项归属、稳定代表节点和必要事件元数据；保持已有 projection 和其他三屏消费者兼容。
2. 事件携带内部 visualKey、已提交活动昵称、questionKey、optionKey、白名单头像引用、事件时间和幂等标识；不携带完整 Participant 对象。
3. 在现有事件控制器内增加有界入场调度，避免重复消费 JOIN / ANSWER / ACTIVE：默认容量 32，过期 5 秒，约 350ms 启动一次，最多 3 个个体入场并行，动态曲线总量不超过 5。
4. 8 人同时更新时，前 2–3 人演示个体动作，其余按场聚合提示；人数始终尽快追踪最新业务快照，不能等待动画队列逐一补账。
5. 同一参与者快速改选时合并到最新选择；移除/离场/换 epoch 时取消失效动作，不能让旧队列把已离场头像重新带回。
6. 进入其他轮播状态或隐藏标签页时，不积压一长串入场动作；返回时恢复当前快照，丢弃过期效果。现有 MATCH 聚合与至少 3 对广播门槛保持原逻辑。

### DOM 与 WebGL

- 新建受控的 `DestinyWorld`，固定 PerspectiveCamera（初始 FOV 35°），只使用浅 Z 层次。无 OrbitControls、后处理、动态阴影、物理引擎或全场景实时 blur。
- PlaneGeometry + ShaderMaterial 绘制低透明暖白核心、有机酒红/暖金细边缘和轻微扩散环；半径按统计归一化并限制 min/max。
- 2 个场左右布置，3 个场三角布置，4 个场松散四象限。舞台限定在标题以下、二维码左侧的现有内容区域，优先减少装饰和隐藏辅助文案以保证阅读。
- DOM 标签通过 Vector3.project(camera) 对齐；标签为静态锚点，头像围绕它漂浮。仅 resize / 布局变化更新投影坐标，不能逐帧 React setState。
- Canvas 使用透明背景、`pointer-events: none`；二维码保持独立 DOM 图片。Canvas 限定内容区并增加边界裁切，不能仅凭二维码 z-index 挡住粒子。
- 背景和 QR 持续挂载。WebGL Canvas 位于 SceneTransition 克隆区域之外；内容切换仍是现有约 800ms Cross Dissolve，不产生空白 Canvas 克隆或旧数字叠影。
- 提供小型视觉宿主协调现有 Canvas 与新 WebGL：question 使用 Three，另外三态保留现有效果；整个视觉宿主只有一个活动帧调度，过渡中的两层由同一调度驱动，非活动场停止绘制。保留 WebGL 资源复用，避免每次轮播重新创建 context。

### 节点、入场和冷启动

- ID 确定稳定抽样顺序和位置参数，禁止 render 中随机重排。基于同一输入可得到一致布局；更新只影响增减节点和必要边界。
- 默认每场最多 10–12 个头像，最大不超过 12；当前入场节点短时保留在样本中，替换最低优先级代表而不突破容量，避免刚入场立即消失。
- 头像漂浮 4–12px / 6–12 秒，场呼吸 8–14 秒，所有节点由同一帧循环更新。
- 单次入场约 1–1.5 秒：出现与曲线行进并行，接近目标时开始轻微 pulse / ring；不能把附件各阶段机械串联成 2–3 秒。人数更新 400–600ms；提示独立停留约 3 秒。
- 0 人时“等待第一个选择”，不展示三组 0%；1–5 人强调人数，6–9 人继续以人数为主且弱显示比例，10 人及以上强化比例。真实人数口径不变。
- 组件输入问题变化：旧场淡出约 400ms，新场进入约 500ms，总体不超过 1.5 秒；相同问题仅局部更新，不销毁重建全部头像。
- 环境粒子默认 30、最高 40，遵循此前用户上限，不采用附件中 60 的可选上限。色彩只用暖白/暖金和极淡酒红。

### 性能、清理与降级

- HIGH：每场 10–12 头像、最多 40 粒子；MEDIUM：8 头像、20–30 粒子；LOW：6 头像、无环境粒子、简化 shader/路径。
- DPR 上限 1.5。持续低帧率时有滞回地逐级降档，不在相邻档位频繁跳动；目标设备 1080p 优先 60FPS，目标底线 30FPS。
- WebGL2 检测失败、创建 renderer 失败或 context 丢失时，使用同一统计投影和代表节点显示 DOM 统计/简化关系场，页面和 QR 仍完整可用；恢复尝试有界，不无限重复创建 renderer。
- WebGL 初始化仅在客户端进行，懒加载限定 `/screen`，不把 Three 打入手机端公共组件；按本仓 Next 16 本地指南处理客户端边界。
- 图片/纹理按 avatarId 缓存共享，不每帧创建 Geometry / Material / Texture。空闲样本不会无限增长缓存；异步加载在卸载后不能重新挂载资源。
- 退出/重置时停止帧循环、解除 observer/listener/subscription，释放独占 geometry/material/texture/renderer；共享资源用明确所有权管理，不能释放仍被使用的纹理。
- Reduced Motion：静态场、静态头像、DOM 人数、QR 保留；关闭漂浮/粒子/呼吸/持续路径和排队动作，仅按数据变更按需渲染。
- 页面隐藏时停帧，恢复时重置时间基准，不累计动画大步长。

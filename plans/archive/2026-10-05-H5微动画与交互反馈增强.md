## 2. 范围与需统一的解释

目标是“选择得到反馈 → 发现共同答案 → 信号发出与到达 → 两条独立轨迹交汇 → 现实见面 → 手机安静下来”。只在双向确认页使用明显的品牌动画，其余页面以可读、快速和克制为准。

1. **保留全部现行业务规则。** 保留昵称 1–5 个汉字、输入法组合输入、系统头像、性别推荐、参与状态、邀请确认、0–3 人推荐及已修正的“返回推荐列表”流程。动画不能写入或推导业务状态。
2. **商户核销、活动通知和婚恋服务两类授权继续延期。** 不因本次文本提到“保持授权逻辑”而重新引入未实现的流程。
3. **所有数字和地点来自实际数据。** 42%、4 道共同答案、37 人、山风、Meet01 都是示例。等待分配时继续显示等待，不能出现“地点已准备好”。
4. **M10 保留已有三个选择。** 仍是“一起走走 / 去云影咖啡 / 就到这里，也很好”，保留独立的“我想继续探索”；不把第三项改成继续认识，也不新增商户选择流程。
5. **大屏复用现有 `MUTUAL` 事件及聚合策略。** 保留 10 分钟内至少 3 对、每组播放 6 秒并消费一次的规则，不另建 `MUTUAL_ACCEPT`。文案沿用适合聚合的“今天，又有人愿意认识彼此”，不把聚合播报说成刚刚某一对。
6. **后台保留现有 Modal。** 当前没有 Drawer，本次只为已有弹层补轻量入场反馈，保持焦点管理和操作习惯，不重排后台结构。
7. **City Response 不能伪装实时。** 目前 ANSWER 事件没有具体答案载荷，不能据此断言“刚刚有人也选了”。本次仅在明确 `isDemoData=true` 的展示层条件下，读取其他参与者已有答案，用“演示数据中，也有人选择了……”；无佐证就不显示，未来真实环境默认关闭。

## 3. Motion System 与实现约束

### 3.1 单一时长与缓动来源

新增 `src/lib/motion-tokens.ts`：

- 基础秒数：`instant=0.12`、`fast=0.18`、`normal=0.28`、`slow=0.45`、`brand=1.4`。
- 缓动：`standard=[0.22,1,0.36,1]`、`enter=[0.16,1,0.3,1]`、`exit=[0.7,0,0.84,0]`。
- 将需求中的特定节奏集中定义为具名语义值：背景 / 数字 0.7 秒、题目切换 0.24 秒、头像 0.25 秒、辨认码 0.3 秒、信号 0.4 秒、标题间隔 0.1 秒、卡片间隔 0.07 秒、答案连线间隔 0.12 秒、Presence 周期 5 秒、提示展示 2 秒。
- CSS 变量和 JS 数值均由这一来源提供；不在各页散写动画时间。品牌流程总长 1.4 秒，分段从同一总时长推导。
- 本次已有的相关按钮、呼吸和关系效果一并纳入统一体系，避免新旧节奏叠加。

### 3.2 公共组件与生命周期

新增 `src/components/motion/`，按使用阶段实现，不一次把所有页面改完：

| 组件 | 职责 |
| --- | --- |
| DestinyTrack | 两条始终可辨的独立 SVG 轨迹；支持静态、绘制和交汇状态，不融合成爱心。 |
| QuestionTransition / DestinyProgressTrack | 题目衔接、六节点进度；完成节点读取已保存答案，当前题位置单独表示。 |
| AnimatedCounter | 初次展示或实际数值变化时轻量插值；环形和数字可共用同一进度。 |
| CommonAnswerLink | 同一道真实共同答案的两端与逐行连线；不凭动画制造共同点。 |
| SignalMotion / SignalArrival | 成功发送与真实收到邀请的不同反馈；失败不播成功动画。 |
| MutualEncounterMotion | 双向确认分阶段绘制及只播放一次的控制。 |
| MeetStatusTrack | 以真实出发 / 到达 / 确认数据展示现实任务状态，无位置推算。 |
| PresenceIndicator / CityResponseToast | 真实参与统计和明确标注的演示回应；不随机增人数、不伪造事件。 |
| RouteDraw | 从实际相遇点到已选择商户的示意连线；不是地图或导航。 |

配套统一的 motion hook / 边界负责：

- 检查 `prefers-reduced-motion`，监听偏好变化；从基础阶段就实现降级，Phase 8 做完整审计。
- 页面隐藏、组件离屏或卸载时停止视觉循环，清理 RAF、监听器和计时器；回到前台展示当前事实，不补播积压的关系事件。
- 动画以 transform、opacity 和 SVG stroke 为主；有限时长的 RAF 仅用于数值或必要路径运动，不使用持续 JS 帧循环。
- 不对整页尺寸、列表高度做逐帧布局动画；短时辨认码字距变化置于固定宽度区域，避免挤动周围内容。
- 交互控件在过渡期间仍可使用。旧题的退出层只作装饰、不可聚焦；新题立即承接状态与焦点，快速连续操作不产生旧内容覆盖。
- 实际值作为可访问文本稳定提供；插值数字仅作视觉展示，避免读屏器逐帧播报。
- 动画结束回调只处理展示状态，不调用答案保存、邀请接受、分配地点、真实见面等业务命令。

### 3.3 成功反馈与播放记录

- **发出信号不拖慢发送。** 保持现有确认弹层；命令成功后立即呈现已发送状态并进入现有等待页。通过移动端共享展示层承接约 0.4 秒信号，让 M06→M07 的视觉过程连续；不为等待光点结束而延迟保存或路由。该层不拦截点击、焦点或返回操作。
- **收到邀请只按新邀请播放。** 同一邀请反复渲染不反复振动；过期、取消、拒绝后立即停止相关到达效果。
- **`hasPlayedMutualMotion` 是展示缓存。** 按演示数据 epoch、当前参与者和邀请 ID 保存，刷新或再次进入直接显示最终态；新邀请可播放一次。放在独立 sessionStorage 展示记录中，不增加用户字段，不修改业务 schema；存储失败时降级为内存记录。
- 在品牌动画开始时登记播放，避免中途离开导致下次强制重播；减少动画模式直接展示最终态并登记已展示。
- 双方确认见面即停止这段关系的轨迹效果。保留 M09→M10 的现有自动路由，M10 可读地承接“双方已确认见面”，不添加人为等待时间。
